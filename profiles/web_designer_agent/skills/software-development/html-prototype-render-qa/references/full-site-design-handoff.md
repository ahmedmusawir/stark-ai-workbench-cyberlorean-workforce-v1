# Selected-foundation full-site design handoff

Use when a reviewed concept becomes the authorized foundation for a complete marketing-site design package. This is a reusable workflow, not a production implementation or QA certification procedure.

## 1. Re-ground authority and protect evidence

Read the current brief, source map, latest ruling and work order. Separate four gates: foundation selection, full-design approval, implementation authorization, publication. Authorization for one does not grant the next. A newer full-design instruction can supersede earlier concept-only bounds without changing the approved route map.

Inspect the named foundation's HTML, tokens/CSS, assets, provenance and desktop/mobile appearance. Render it again into the NEW package before extending. Hash authorized source inputs before writing; keep old packages read-only. Do not claim that every protected package was hash-checked if only the selected foundation was hashed. Do not touch unrelated investigation output.

Independent exploration is a different mode: when prior outputs are forbidden, do not open an old package even to borrow its verification harness or asset paths. Use skill-owned reusable tools and permitted original inputs. Conversation history is not erasable; never claim a scientifically blinded experiment.

## 2. Build an artifact matrix before generating

One row per approved route:

| Route | Prototype | Required substantive sections | Exact evidence | Desktop PNG | Mobile PNG | Viewed / tested |
|---|---|---|---|---|---|---|
| Public route | Actual local file | Named sections, not just a hero | File + section/lines | Actual path | Actual path | Separate visual/technical status |

Enumerate every page in the task checklist. Do not collapse a multi-page assignment into one generic service template. Retain the selected visual vocabulary while varying the page's content rhythm: sequence, rail, editorial directory, task spread, FAQ, contact sheet, etc.

Use a distinct review filename such as PACKAGE_INDEX.html; it must not replace Home. Flat prototype files are valid when documented as mappings rather than changed public URLs. Provide a working local serving command. Optional HTTP smoke checks can use an ephemeral localhost-only server and shut it down in a finally block; serving mapped files is not proof that public-route rewriting exists.

## 3. Content contract and provenance

Store page content plus shared phone/address/provisional notices, footer and CTA settings in structured local files. Do not scatter editable business facts through template code and then claim the whole site is data-driven. Template/layout hooks remain code-owned.

For EVERY actual section, record:
- page and stable section ID;
- source-map row;
- exact evidence file and captured section/line range;
- retain/rewrite/combine/design-authored disposition;
- proposed fields and image slot rules;
- meaningful source omissions.

A supported headline/process interpretation need not be a quotation. Conversely, preserving a source's process titles/order does not make rewritten bodies “verbatim.” Preserve useful detail while removing unsupported guarantees, outcomes, cadence or absolute promises. If a work order's capability count includes both service operations and campaign formats, make that accounting explicit rather than inventing extra source headings.

Missing dedicated-page evidence can be assembled from specific captured Home paragraphs, but cannot justify new prices, tiers, SLAs, turnaround, hours or security promises. Where named integrations/portfolio rights are absent, do not fill the gap with endorsement logos or fabricated client work.

## 4. Token and asset quality

Keep one canonical semantic token file plus an explicit Tailwind-version assumption/map. Do not introduce self-referential aliases: `--text-body: var(--size-body)` is safe; `--text-body: var(--text-body)` is cyclic. Measure each actual foreground/background context; a brand accent swatch label can fail even when all marketing CTAs pass.

Artwork legibility is its own review: a white folded plane may vanish against a white page while text contrast, overflow and image decode all pass. Use an intentional subtle paper surface/shadow or change the presentation; then inspect both sizes. Never infer artwork visibility from a passing accessibility scan.

Preserve logo bytes and aspect ratio; use a backing surface on dark blocks rather than recoloring. Inventory all delivered binaries, including archived reference-only fonts: include applicable notices or exclude unnecessary copies. An unused archival asset is still redistributed.

## 5. Rendering sequence and verification

1. Generate the active pages and required linked documents.
2. Render every approved page at desktop/mobile with fonts ready and images decoded.
3. Render nested style tiles explicitly. The bundled renderer accepts a file or directory; the observed preflight CLI expects a directory. Match each tool's own arguments rather than assuming interchangeable entry shapes.
4. Refresh reviewer screenshots AFTER their page-PNG dependencies exist, or previews can be blank/stale.
5. View every page's overall composition and readable hero/lower-content regions. A very tall full-page render downscaled to a narrow strip is an inventory check, not a legibility check.
6. Recheck intermediate widths and expanded menus/FAQ answers. Include nested tile and review surfaces in the test matrix.
7. Preserve the failing first pass before repairs; fix the author/generator, not generated files alone.

Two-dimensional targets must be tested at all widths. A footer's short “SEO” link can measure 26×44px at desktop because align-items:start makes its width content-sized, while its mobile grid cell meets the floor. Apply min-width:44px and verify again; do not conclude mobile success covers desktop.

For native disclosures, send actual complete keyboard input and assert details.open, Escape close/focus return, expanded reflow and contrast. Scan customer-facing text after opening answers: closed innerText alone misses prohibited hidden content. Also inspect provenance leakage such as “the captured three-stage approach”; replace it with customer language and keep its evidence explanation in the manifest. Use word-boundary regression fixtures so legitimate “Facebook advertising” stays allowed.

Treat CSS class warnings contextually: a root-only scan may exclude tile-only markup, and a tile-only scan naturally finds shared site classes unused. Identify behavior hooks and parser filename fragments explicitly; do not suppress unexplained warnings.

## 6. Revisions and completion

Separate Director decisions from Designer refinements. Record full date/timezone, source/quote, exact adjustment, affected files and superseded version. Snapshot the preceding source/content/assets/render set before applying direct changes. An adjustment request is not final approval.

Stamp deliverables and handoffs with Version and full Updated timestamp. A screenshot manifest can record dimensions, scale, hashes and renderer; optional PNG text metadata must not be presented as a new render. Record observable session model/provider labels separately from independently verified response identity; mark unexposed effort/usage/cost unknown. Capture actual start/end observations and calculate wall-clock elapsed with a tool.

Final handoff should contain the exact review entry, complete route/file/render coverage, token/spec/manifest/asset locations, actual technical results, separate visual judgment, source/reconciliation gaps and next owner. Report large test counts as repeated assertions across pages/links/states—not independent acceptance criteria or proof of visual quality. Verify ZIP integrity and compare required archive members with the final files before delivery. Stop for the requested design/Architect gate; do not silently release implementation.
